# Color calibration: reference material, kits, and how to reproduce them

This project fits interpretable camera→reference colour mappings from a
reference chart and applies them to product images. It never ships a single
"ideal corrected image": every output carries measured error, and every
fixture is rebuildable from saved parameters.

## What lives where

| Path | Purpose |
| --- | --- |
| `colorcalib/` | The kernel: colour spaces, detection, fitting, validation, application, HTML report. |
| `web/` | Flask image-calibration UI (single-chart fit + cross-camera kit panel). |
| `scripts/make_synthetic.py` | Legacy single-camera scenario generator (7 synthetic scenes). |
| `scripts/run_legacy_example.py` | Re-runs the legacy example end to end and checks the checked-in PNGs still match a fresh render. |
| `scripts/build_camera_kit.py` | Builds a camera kit's images from `kit_params.json` (byte-reproducible). |
| `scripts/rebuild_camera_kit.py` | Rebuilds mappings from a kit and verifies the agreed contract; writes `kit_verification.json`. |
| `camera_kits/dual_camera_kit/` | The fictional dual-camera material pack (charts, scenes, negative control, params, manifest, README). |
| `examples/` | The original single-camera example inputs and outputs (unchanged). |
| `tests/` | Kernel tests plus kit/cross-camera/web tests. |

## Which differences are simulated responses

The dual-camera kit is **entirely synthetic**. Every image in
`camera_kits/dual_camera_kit/` is generated by `colorcalib/simulate.py` from
`kit_params.json`, and the manifest marks every file
`"simulated_response": true`. The effects that make camera A, camera B, and
the foreign camera differ are explicit and listed in the manifest's
`simulation_models`:

- camera colour mixing — a fixed 3×3 matrix per camera in linear light;
- illumination / white balance — per-channel gains plus exposure;
- sensor noise — seeded Gaussian;
- black level — linear offset before clipping;
- matte patches with synthetic border/background.

The legacy `examples/` scenarios use the same idea with a single camera and
seven lighting/exposure/defect variations. They are also simulated; nothing
here is a photograph.

## Reproduce (scripts, not a frozen image)

```bash
# rebuild the kit's images from its saved parameters (byte-identical)
PYTHONPATH=. python scripts/build_camera_kit.py --kit camera_kits/dual_camera_kit

# re-fit every camera/illumination and verify the contract; exit 0 = pass
PYTHONPATH=. python scripts/rebuild_camera_kit.py \
    --kit camera_kits/dual_camera_kit --out /tmp/kit_check

# re-run the legacy single-camera example end to end; exit 0 = pass
PYTHONPATH=. python scripts/run_legacy_example.py --examples examples

# full test suite (kernel + kit + web surface)
python -m pytest -q
```

`rebuild_camera_kit.py` writes `kit_verification.json` with, per
camera/illumination: re-render pixel-diff vs disk, train/CV/**holdout** ΔE2000,
recovered vs true camera matrix, and per-block **scene residuals tied to exact
pixel rectangles**. It also records the positive control (same camera across
illumination) and the negative control (foreign camera), and exits non-zero if
either contract is violated.

## Independent check (not a training residual relabelled)

`calibrate(..., holdout_indices=[...])` removes those patches from the
production fit, from white-balance estimation, and from the cross-validation
folds. Their errors appear in `holdout_summary` and per-patch under role
`holdout`. The dual-camera kit declares `blue_sky`, `orange_yellow`, `cyan`,
`neutral_7_5` as its holdout set. This is the "independent colour residual"
used throughout the kit verification and the UI.

## Cross-camera contract

A mapping carries the **sensor → reference colour transform**; white balance
is re-derived from the target image's own neutral patches. Consequences:

- the same camera transfers across illuminations (mean ΔE ≈ 2.5 in the kit),
- a different camera does not (full-chart mean ΔE ≈ 12 and up; the kit's
  negative control is rejected),
- the UI labels the measured outcome `consistent` / `weak` / `mismatch` and
  never overrides the number with a default.

Thresholds are in `kit_params.json` → `acceptance`; the verifier reads them.

## Start the interface

```bash
PYTHONPATH=. python -m web.app --host 127.0.0.1 --port 5000
```

Open <http://127.0.0.1:5000>. The **"Cross-camera kit"** panel:

1. pick `dual_camera_kit`,
2. pick a source chart (fitted) and a target chart (applied) — a different
   camera is pre-selected so the first run is a real transfer,
3. click swatches in the **Holdout patches** strip (declared holdouts are
   pre-selected),
4. optionally paste manual corners,
5. click **Calibrate across cameras**.

Previews show the source chart, the target chart, and a mapped **cross-camera
sample** (target scene) with per-block ΔE and pixel rectangles. The table lists
every target-patch colour residual, holdout rows highlighted. Failures still
surface: a foreign target reads `mismatch`, and a refused fit returns the
kernel's message.

## Kernel drives the UI

The cross-camera route calls the same `calibrate` kernel used by the CLI and
scripts; it does not hard-code coefficients. The target application reuses the
shared `scene_white_gains` guard rail, so an insufficient neutral row produces
unity gains **and** a warning that is shown in the UI, never a silent default.
